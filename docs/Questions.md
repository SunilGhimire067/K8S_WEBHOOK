In Kubernetes, different services show different latencies because each service has a unique processing pipeline — some services are lightweight (e.g., a simple nginx returning a static page responds in ~20ms) while others do heavy work on each request (e.g., a backend service that connects to a database, runs queries, and processes data takes ~600ms+). The latency measured by curl -w '%{time_total}' includes everything: DNS resolution, TCP handshake, the service actually processing the request and sending a response back. So the variation isn't about network speed between pods (which is typically sub-millisecond within a cluster), it's about how long each target service takes to respond. Two services on the same node with identical network paths will still show vastly different latencies if one is a fast proxy and the other is a slow application. That's why in real monitoring, you'd compare a service's latency against its own baseline, not against other services.

The JVM Details page works by comparing what you configured vs what's actually running inside Java pods.

Expected (ENV) is extracted by reading the pod's environment variables (JAVA_OPTS, JAVA_TOOL_OPTIONS, JVM_OPTS, _JAVA_OPTIONS) via kubectl get pod -o json and parsing JVM flags like -Xmx1200m, -Xms256m, -XX:MaxMetaspaceSize=128m from those env var values. Actual (Runtime) is obtained by executing kubectl exec <pod> -- jcmd 1 VM.flags inside the running container, which asks the JVM process itself to report its active flags (with a fallback to reading /proc/1/cmdline if jcmd isn't available). The backend then parses both sets of flags into a normalized map (Xmx, Xms, MaxMetaspaceSize, GC) and compares them — in your screenshot, the env vars say -Xmx1200m but the JVM is actually running with -Xmx512m, which means either the env var isn't being picked up by the application's entrypoint script, or another configuration (like a JVM ergonomics auto-sizing or a different startup script) is overriding it. The Mismatch badge appears whenever any expected value differs from the actual value, which is critical to catch because your pod thinks it has 1200m heap but is actually running with only 512m — potentially causing OOM kills or performance issues that are hard to debug without this comparison.
