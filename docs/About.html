API Communication Flow

End-to-End Data Flow

1. EVENT CAPTURE
   K8s Cluster → event_watcher.py streams events
   → webhook_receiver.py classifies severity
   → stores in k8s_events.db

2. USER LOGIN
   Browser → POST /api/auth/login → TOTP verify → session token in localStorage

3. DASHBOARD VIEW
   DashboardPage → parallel fetch: event stats + events + nodes

4. AI ANALYSIS
   User message → POST /api/chat → system prompt + LLM with 10 tools
   → tool loop (max 10 rounds) → markdown response

5. REMEDIATION
   LLM calls apply_fix(dry_run=True) → user confirms
   → apply_fix(dry_run=False) → mark_resolved(event_id)

Webhooks & Event Collection

webhook_receiver.py (Port 8000)

  • Receives K8s events via POST /webhook/event
  • Classifies severity: critical warning info
  • Stores in SQLite with 16-char hash event_id, timestamps, status

event_watcher.py (CLI)

  • Runs kubectl get events --watch -o json
  • Parses streaming JSON and POSTs each event to port 8000
  • Supports --namespace filtering

Security Considerations

Authentication

  • Two-factor authentication: password + TOTP (RFC 6238)
  • Session tokens: 64-char hex, stored in-memory (cleared on restart)
  • All protected endpoints require Authorization: Bearer <token>

Tool Safety

  • get_cluster_info: Read-only kubectl commands only (get, describe, logs, top)
  • apply_fix: Defaults to --dry-run=client, blocks destructive commands
  • Tool results truncated to 8,000 chars to prevent context overflow
  • Max 10 tool rounds per chat session

Network

  • CORS enabled (configurable origins)
  • SQLite WAL mode for safe concurrent access
  • No secrets in code — all via environment variables

1. Project Overview

Sentinel K8s is a full-stack Kubernetes cluster monitoring dashboard with AI-powered event analysis. It combines real-time event tracking, cluster observability, and an intelligent chat assistant that can diagnose issues, suggest fixes, and execute remediation commands.

Core Capabilities

  • Real-time Event Monitoring — Captures and classifies Kubernetes events (critical/warning/info) with live streaming
  • Cluster Observability — Node status, pod management, log viewing, namespace exploration
  • AI-Powered Diagnostics — Multi-turn LLM chat with 10 specialized tools for cluster analysis
  • Resource Allocation — Live CPU/memory usage vs requests/limits with progress bars and AI-powered resource trace
  • JVM Configuration Audit — Compare expected (env vars) vs actual (runtime) JVM flags for Java pods
  • Network Observability — Cross-namespace latency testing (source pod → target services), network policies, endpoint health
  • Automated Remediation — AI can suggest and execute fixes with dry-run safety
  • Two-Factor Authentication — TOTP-based 2FA compatible with Google Authenticator
  • Claude Desktop Integration — Same 10 tools available via MCP protocol

Integration Flow: chat_ui ↔ Claude Desktop via MCP

Both the web dashboard and Claude Desktop share the same 10 analysis tools and the same database. The difference is the transport:

  • Web Dashboard: Frontend → POST /api/chat → chat_handler.py → tool_executor.py → mcp_server.py functions (direct import)
  • Claude Desktop: Claude → MCP protocol (stdio) → mcp_server.py → same functions

The tool_executor.py in the backend adds the parent directory to sys.path and directly imports the tool functions from mcp_server.py, ensuring both paths execute identical logic.

3. Data Flow

Event Collection Pipeline

  1. K8s Cluster emits events (pod created, node unhealthy, etc.)
  2. event_watcher.py runs kubectl get events --watch -o json, parses the streaming JSON output
  3. Each event is sent via HTTP POST to webhook_receiver.py at port 8000
  4. webhook_receiver.py extracts fields (kind, name, namespace, reason, message), classifies severity, generates a 16-char hash event_id, and inserts into SQLite

User Authentication Flow

  1. User submits username + password → POST /api/auth/login
  2. Backend validates credentials, generates a temp_token (64-char hex)
  3. First login: returns QR code (base64 PNG) for Google Authenticator setup
  4. User submits 6-digit TOTP code → POST /api/auth/verify-totp
  5. Backend validates TOTP code, issues session token stored in _tokens set
  6. Frontend stores token in localStorage["auth_token"]
  7. All subsequent API calls include Authorization: Bearer <token>

AI Chat Flow

  1. User types a message or clicks a skill button on AIInsightsPage
  2. Frontend sends message history via POST /api/chat
  3. chat_handler.py detects skill prefix [Label] and expands to full prompt
  4. System prompt from system_prompt.md is prepended
  5. Messages sent to LLM via OpenAI-compatible API (through LiteLLM proxy)
  6. LLM responds with optional tool_calls (e.g., list_events, analyze_event)
  7. tool_executor.py dispatches each tool call to the corresponding function in mcp_server.py
  8. Tool results are appended to the conversation and sent back to the LLM
  9. Loop continues (max 10 rounds) until LLM responds without tool calls
  10. All new messages (assistant + tool) are returned to the frontend
  11. Frontend renders messages with markdown and collapsible tool call cards

Page Details

LoginPage

Three-step UI: (1) credentials form, (2) QR code setup for first-time TOTP, (3) 6-digit code entry with auto-submit.

DashboardPage

Four stat cards (Total/Critical/Warning/Normal), recent events table (click navigates to AI Insights), node status table.

EventExplorerPage

Severity filter buttons, text search, LIVE toggle (auto-polls every 5s), event table with severity badges. Clicking a row navigates to /ai-insights?event={id}.

NodesPage

Table of cluster nodes: name, status (Ready/NotReady with color indicator), roles, K8s version, OS, kernel, container runtime.

LogsPage

Cascading dropdowns: Namespace → Pod. Selecting a pod auto-fetches last 200 log lines in a monospace viewer.

ResourceAllocationPage

Namespace dropdown filter, auto-refresh toggle (15s), table of pods showing CPU/memory usage vs requests/limits with colored progress bars (green <70%, amber 70-90%, red >90%). "Trace" button on high-usage pods opens a modal with AI-powered root cause analysis from the LLM.

JvmDetailsPage

Namespace dropdown filter, table comparing expected JVM flags (from env vars: JAVA_OPTS, JAVA_TOOL_OPTIONS) vs actual runtime flags (via jcmd). Mismatch rows highlighted in amber. Expandable rows show raw env vars and jcmd output.

NetworkLatencyPage

Separate Source (namespace + pod dropdown) and Target (namespace dropdown) controls for cross-namespace latency testing. Services table with endpoint status. "Test Latency" button runs curl from the selected source pod to all target services (self-service tests auto-skipped). Each latency result has a "Check" button that opens a modal showing the full test process: source/target details, kubectl exec command, curl flags explained, and cross-namespace badge. Also includes network issues and network policies sections.

AIInsightsPage

Full chat interface with skill bar, message bubbles (markdown rendered), collapsible tool call cards, and animated loading indicator. Auto-triggers analysis when ?event={id} URL param is present.

How It Works

  1. Claude Desktop launches the MCP server as a subprocess
  2. Communication happens via stdio (JSON-RPC over stdin/stdout)
  3. When a user asks about Kubernetes in Claude Desktop, the model can invoke any of the 10 tools
  4. The MCP server reads from the same k8s_events.db as the webhook receiver

  2. Update the command path to point to the project's Python interpreter
  3. Update the args path to point to mcp_server.py
  4. Set KUBECONFIG to your kubectl configuration file
  5. Restart Claude Desktop to load the new MCP server

10. Webhook Setup

webhook_receiver.py

FastAPI service (port 8000) that receives Kubernetes events via HTTP POST.

Endpoints

  • POST /webhook/event — Receives K8s event JSON payload
  • GET /health — Health check

Event Processing Pipeline

  1. Receives event JSON from event_watcher or kube-event-exporter
  2. Extracts fields: kind, name, namespace, reason, message
  3. Classifies severity based on the reason field
  4. Generates a 16-character hash as event_id
  5. Stores with ISO 8601 timestamps and initial status "new"

event_watcher.py

CLI tool that streams events from a Kubernetes cluster:

  1. Runs kubectl get events --watch -o json as a subprocess
  2. Parses streaming JSON events line by line
  3. POSTs each event to webhook_receiver at port 8000
  4. Supports --namespace flag for namespace filtering

Kubernetes Event Exporter (Alternative)

The k8s-manifests.yaml includes a kube-event-exporter deployment that can replace event_watcher.py for in-cluster event collection. It forwards events to the webhook receiver's ClusterIP service.

Frontend State

AuthContext (context/AuthContext.tsx)

React Context providing authentication state across the app:

  • State: token (string | null), isAuthenticated (boolean)
  • Methods: login(username, password), verifyTotp(tempToken, code), logout()
  • Persistence: Token stored in localStorage["auth_token"]

React Context managing chat state for the AI Insights page:

Each page manages its own data via useState and useEffect. No global state library (Redux, Zustand, etc.) is used. Data is fetched on mount and refreshed as needed.

  • SYSTEM_PROMPT: Module-level string loaded from system_prompt.md on startup
  • SKILLS: Module-level dict loaded from skills.yaml on startup
  • SQLite DB: Persistent event storage (survives restarts)
  • .totp_secret file: Persistent TOTP secret (survives restarts)

14. Authentication Mechanism

Two-Factor Authentication (TOTP)

Login uses a two-step process based on TOTP (RFC 6238), compatible with Google Authenticator, Authy, and similar apps.

Step 1: Password Validation

POST /api/auth/login
Body: { "username": "admin", "password": "admin" }

Response (first time):
{
  "temp_token": "<64-char hex>",
  "requires_totp": true,
  "setup_required": true,
  "qr_image": "<base64 PNG>",
  "secret": "JBSWY3DPEHPK3PXP..."
}

Response (returning user):
{
  "temp_token": "<64-char hex>",
  "requires_totp": true,
  "setup_required": false
}

Step 2: TOTP Verification

POST /api/auth/verify-totp
Body: { "temp_token": "<64-char hex>", "code": "123456" }

Response: { "token": "<64-char hex session token>" }

Session Management

  • Session tokens are 64-character hex strings stored in an in-memory _tokens set
  • Tokens are cleared on backend restart (users must re-login)
  • Frontend stores token in localStorage["auth_token"]
  • All protected endpoints require Authorization: Bearer <token>
  • require_auth() FastAPI dependency validates the token on every request

TOTP Secret Storage

LocationDataLifetime
chat_ui/backend/.totp_secretBase32 TOTP secretPermanent (survives restarts)
Google Authenticator (phone)Same secret as QRUntil manually removed
Backend _tokens setSession tokensUntil backend restart
Browser localStorageSession tokenUntil logout or manual clear

Reset 2FA

Delete chat_ui/backend/.totp_secret and restart the backend. The next login will show the QR setup screen again.

18. Database Schema

SQLite Database: k8s_events.db

Located at project root. WAL mode enabled for safe concurrent reads/writes across multiple processes.

CREATE TABLE k8s_events (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    event_id    TEXT UNIQUE NOT NULL,     -- 16-char hash
    event_type  TEXT NOT NULL,            -- "k8s-event", "admission", "alert"
    kind        TEXT,                     -- "Pod", "Node", "Deployment", etc.
    name        TEXT,                     -- resource name
    namespace   TEXT,                     -- K8s namespace
    reason      TEXT,                     -- "CrashLoopBackOff", "Pulled", etc.
    message     TEXT,                     -- full event message
    severity    TEXT DEFAULT 'info',      -- "info", "warning", "critical"
    raw_payload TEXT NOT NULL,            -- full JSON payload
    status      TEXT DEFAULT 'new',       -- "new", "analyzed", "resolved"
    analysis    TEXT,                     -- analysis notes (set by analyze_event)
    created_at  TEXT NOT NULL,            -- ISO 8601 timestamp
    updated_at  TEXT NOT NULL             -- ISO 8601 timestamp
);

CREATE INDEX idx_status   ON k8s_events(status);
CREATE INDEX idx_severity ON k8s_events(severity);
CREATE INDEX idx_created  ON k8s_events(created_at);

19. AI Tool System (10 Tools)

The LLM has access to 10 tools that it can call autonomously during a conversation. These tools are available in both the web dashboard (via tool_executor.py) and Claude Desktop (via MCP server).

#ToolParametersDescription
1list_eventsstatus, severity, namespace, limitBrowse events with filters
2get_eventevent_idGet full details of a specific event
3analyze_eventevent_idRun diagnostics, get suggested fixes, mark as analyzed
4get_cluster_infocommandRun read-only kubectl (get, describe, logs, top, version)
5apply_fixcommand, dry_runExecute kubectl fix — dry-run by default for safety
6mark_resolvedevent_id, resolution_noteMark event as resolved after fix
7get_event_summary—Dashboard overview: counts by severity/status + latest 5 events
8trace_resource_usagepod, namespaceGather describe, top, events, logs for a pod — return root cause analysis
9get_jvm_detailsnamespaceScan Java pods, compare expected vs actual JVM flags, report mismatches

Safety Mechanisms

  • get_cluster_info: Only allows read-only kubectl subcommands (get, describe, logs, top, version). Blocks write operations (delete, apply, patch, edit, create).
  • apply_fix: Defaults to dry_run=True, appending --dry-run=client. User must explicitly confirm before live execution. Blocks destructive commands (delete namespace, drain, cordon, taint).
  • Tool result truncation: Results over 8,000 characters are truncated to prevent LLM context overflow.
  • Max 10 tool rounds: The chat loop stops after 10 LLM ↔ tool iterations to prevent infinite loops.

Analysis Templates

The analyze_event tool provides specialized diagnostics based on the event's reason:

20. Security Considerations

Authentication

  • Two-factor authentication: password + TOTP (RFC 6238)
  • Session tokens: 64-char cryptographic hex, stored in-memory (not in DB)
  • Temp tokens: Single-use, cleared after TOTP verification
  • All protected endpoints require Authorization: Bearer header
  • TOTP secret persisted to file (survives restarts), session tokens do not

Tool Execution Safety

  • get_cluster_info: Whitelist of read-only kubectl subcommands
  • apply_fix: Dry-run by default, blocklist of destructive commands
  • Result truncation to 8,000 chars prevents context overflow
  • Max 10 tool rounds prevents infinite loops

Network Security

  • CORS middleware configured (currently allows all origins for development)
  • No secrets in source code — all credentials via environment variables
  • SQLite WAL mode for safe concurrent access
  • Webhook receiver is unauthenticated (intended for internal/cluster use)

Recommendations for Production

  • Restrict CORS origins to specific domains
  • Add authentication to webhook receiver endpoint
  • Use HTTPS for all external communication
  • Store session tokens in a persistent store (Redis) for multi-instance deployments
  • Rotate LITELLM_API_KEY periodically
  • Implement rate limiting on authentication endpoints
